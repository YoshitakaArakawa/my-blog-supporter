# wix-sync 改修設計: 拡張 Markdown と往復で落とさない同期

- 状態: 案（著者の承認待ち）。実装はまだしない
- 作成: 20261107
- 対象: `.claude/skills/wix-sync/`、`scripts/render-preview.mjs`、`scripts/lint-draft.mjs`、`scripts/draft-lint.config.json`、`scripts/revise.mjs`、`.claude/skills/revise`・`.claude/skills/article` の Wix への言及

## 結論

正本は Markdown のまま保つ。Ricos JSON は運搬と控えの層に留める。

そのうえで、次の4つを入れる。

1. **拡張記法**: 文字色・下線・画像の幅・X の埋め込みを Markdown に書ける記法を足す（[記法](#記法の案)）
2. **自前の変換器**: Markdown → Ricos を、Wix の変換 API ではなくリポ内のコードで行う（[変換の流れ](#変換と保存の流れ)）
3. **落ちる段落の控え**: pull の時点で「Markdown から同じノードに戻せない段落」だけを控え、文字が変わっていなければ控えのまま送る。変わっていれば黙って落とさず止める
4. **画像は ID で戻す**: Wix 上の画像を、出てくる順番ではなく Media の ID で Markdown に書く

1 と 2 で「書ける装飾」を増やし、3 で「まだ書けない装飾」を守る。4 は今回のずれを直接止める。

公開済み記事の更新は、公開中の記事の下書きを API で直接置き換えるのを既定にする（著者の判断 20261107）。試しの下書きは作らない。この既定は 3 と 4 が入って初めて無確認で成り立つので、それまでは dry-run の点検で補う（[公開済み記事の更新](#公開済み記事の更新)）。

## 背景: 何が落ちたか

2026年10月に、公開済みの記事（Tableau プラグインの記事）の改訂版を Wix に送った。公開版の控え（pull の JSON）と、送った内容（`push --dry-run` の JSON）を比べると、差は次の4種だった。

| 種類 | 公開版 | 送った内容 | 原因 |
|---|---|---|---|
| 文字色 `#E65100` | 6か所（うち1か所は太字と併用） | 0 | pull が COLOR を Markdown に書かない |
| 段落内リンクの下線 | リンク14件すべてに UNDERLINE | コードブロック内の7件だけ | 変換 API は LINK に UNDERLINE を付けない。Wix の編集画面は付ける |
| 画像の幅 | SMALL / CONTENT を著者が選択 | 一律 CONTENT | 幅を控えていなかった（PR #13 で修正。下記） |
| キャプション無しの Wix 画像 | 本来の画像 | 後ろの画像にずれた | 空キャプション同士を出てくる順で割り当てていた |

画像の幅は、PR #13（ブランチ `wixsync-keep-image-size`、20261107 時点で未マージ）で、pull が `wix.json` の `images[].container` に控え、push がそれを使うように直した。この設計はその修正を前提にし、[段階1](#移行の手順)で記法に置き換える。

文字色6か所と下線5か所は、送った後に下書きの Ricos JSON を API で直接直して戻した。公開版の控えにある装飾を、該当する TEXT ノードに足して PATCH した。[段階3](#移行の手順)の「変えていない段落は控えのまま送る」が入れば、この後処理は要らなくなる。

この改訂では、装飾が落ちるかを確かめるため、まず別の非公開の下書きに push した。結び付けの切り替えと後片付けが増えた。最終的には公開中の記事の下書きへ `push --update --allow-published` で送った。この経路は置き換える前に記事を非公開の複製として残し、公開版は著者が Wix で公開するまで変わらない。この安全策があれば、試しの下書きは要らない。

X の埋め込み（HTML ノード）は往復では保たれていた。ただし Markdown 上は `<!-- Wixのノード: HTML #0 -->` の印だけで、新しく書く手段が無い。

## 判断: JSON を正本にしない

JSON を正本にすると、Markdown を前提にした工程がすべて作り直しになる。代わりに得るものは「装飾を落とさない」だけで、これは控え（下記の3）でも得られる。

- lint（`lint-draft.mjs`）・プレビュー（`render-preview.mjs`）・差分（`revise.mjs`）は Markdown を読む
- 著者と AI が本文を読み書きするのも Markdown。Ricos JSON は1段落が数十行になり、人が読んで直せない
- `published/` の公開層も Markdown で残している

したがって JSON は「Wix とやりとりする形」と「戻すための控え」に限る。

## 記法の案

方針は3つ。

- **既存の Markdown 記法に寄せる**: 属性は Pandoc / markdown-it-attrs の `{...}`、ブロックは remark-directive の `::名前{...}` の形を借りる。独自の文法を一から作らない
- **意味で名前を付ける**: 色は `{.accent}` のように名前で書き、色の値は設定ファイルに1か所だけ置く。本文に `#E65100` を散らさない
- **書かなければ既定**: 属性を書かない画像・リンクは今と同じ結果になる。既存の記事はそのまま通る

### 文字色と下線（インライン）

```markdown
この記事では[スマホのブラウザだけ使って]{.accent}、ダッシュボードを作ります。

**[サイトURIは、後でサインインするときに使います。]{.accent}**

[ここは下線だけ]{.u}、[色と下線を両方]{.accent .u}。

[任意の色]{color=#1565C0}
```

- `[テキスト]{.accent}` → COLOR（foreground は設定の `accent` の値）
- `[テキスト]{.u}` → UNDERLINE
- `{color=#RRGGBB}` は名前の無い色の逃げ道。pull で設定に無い色が来たらこの形で書く
- 太字・斜体との併用は外側に `**` / `*` を置く
- 名前と色の対応は `scripts/wix-styles.json`（新設）に置く。例: `{ "accent": { "color": "#E65100" } }`

`[テキスト](URL)` のリンクとは、直後が `(` か `{` かで区別する。`[テキスト]` だけの行（角括弧の地の文）は従来どおり地の文のまま。

リンクの下線は記法にしない。Wix の編集画面がリンクに必ず下線を付けるので、push が全リンクに UNDERLINE を付ける（コードブロックの中のリンクと同じ扱い）。

### 画像の幅と Wix 上の画像

```markdown
![手順の画面](images/step-01.png "ページを開いたら「参加」を押す"){width=small}

![](wix:xxxxxx_0123456789abcdef~mv2.png){width=small}

![参考](wix:xxxxxx_fedcba9876543210~mv2.png "参考：[スキルとは何ですか？](https://example.com/skills)")
```

- `{width=small|content|full|original|<数値>}` → `containerData.width`（`size` または `custom`）。省略時は今の既定（縦長は small、それ以外は content）
- `{align=left|center|right}` も受け付ける。省略は center
- `wix:<Media の ID>` は、著者が Wix で入れた画像。今の `<!-- 画像: キャプション -->` とキャプション行の2行を、この1行に置き換える
- キャプションは title（`"..."`）に書き、中のリンク・太字も解釈する。キャプション中の `"` は `\"` と書く

ID で書くので、プレースホルダーを消しても後ろの画像はずれない。プレビューも `wix.json` を読まずに `https://static.wixstatic.com/media/<ID>` で表示できる。

### 埋め込み（ブロック）

```markdown
::x{url="https://x.com/example/status/1234567890" width=500 height=693}

::html{id=abcd1234567}
```

- `::x{url=...}` → X のポストを、Wix の編集画面が作るのと同じ HTML ノード（`<blockquote class="twitter-tweet">` と widgets.js）にする。`width`・`height` は省略可で、省略時は幅 500・高さは仮の値（[未検証](#未検証の前提)）
- pull は、HTML ノードの中身が X のポストの埋め込みなら URL と寸法を取り出して `::x` で書く
- それ以外の HTML ノードは `::html{id=...}` にする。中身は `wix.json` にノードの ID で控える。今の `<!-- Wixのノード: HTML #0 -->`（pull ごとの連番）を置き換える
- 将来 YouTube（VIDEO ノード）などを足すときも `::名前{...}` の形で増やす。この段階では作らない

### 書かないもの

次は Markdown に書く記法を作らず、控え（下記）で守るだけにする。使用頻度が低く、記法を増やすほど本文が読みにくくなるため。

- 文字サイズ、背景色（ハイライト）、行揃え、段落の行間
- コードブロックの中の太字・リンクの無い下線（今の CODE_BLOCK の控えを一般化する）

## 変換と保存の流れ

### push（Markdown → Wix）

1. **解析**: 拡張記法を含む Markdown をブロック列にする（見出し・段落・リスト・引用・区切り線・コード・画像・埋め込み・空段落の印）
2. **ノード化**: 各ブロックを Ricos ノードにする。リンクは新しいタブ＋下線、`{.accent}` は COLOR、画像は `wix:` ならその ID、ローカルなら上げた ID
3. **控えとの照合**: 各ブロックの「正規化した Markdown」のハッシュを、pull で控えたブロックと照合する。一致し、かつそのブロックが控え対象（戻せない装飾を持つ）なら、控えのノードをそのまま使う
4. **控え対象なのに文字が変わったブロック**: 止める。落ちる装飾（例: 「文字サイズ 2か所」）と行番号を出し、Wix で直すか、装飾を捨てるかを著者に返す。今の CODE_BLOCK の振る舞いを全ブロックに広げたもの
5. **空段落**: 今の既定と印をそのまま使う
6. **送信**: 今と同じ（新規は POST、更新は PATCH の `action: UPDATE`。直前の下書きを `wix-snapshots/` に残す）

照合は「位置」ではなく「中身のハッシュ」で行う。段落を足す・消す・入れ替えても、文字が同じ段落は控えに当たる。同じ文字の段落が複数あれば、先頭から順に使う（中身が同じなので取り違えても結果は同じ）。

### pull（Wix → Markdown）

1. 各ノードを拡張記法の Markdown にする
2. **往復の検算**: その Markdown を push と同じ手順でノードに戻し、元のノードと比べる（`id` とキーの順は無視）
3. 一致しないブロックだけを `wix.json` の `blocks` に控える: `{ hash: <正規化 Markdown のハッシュ>, lost: ["FONT_SIZE", ...], node: <元のノード> }`
4. 控えたブロックの数と落ちうる装飾を出力に出す（例: 「戻せない装飾のある段落 2: 文字サイズ」）

この検算により、「pull した直後の Markdown を何も変えずに push すれば、Wix の下書きは変わらない」が機械的に保証される。今は CODE_BLOCK と HTML だけが控えの対象で、段落の装飾は無言で落ちていた。

### 変換 API をやめて自前で変換する理由

今の push は Wix の変換 API（`/ricos/v1/ricos-document/convert/to-ricos`）に Markdown を送り、返ってきたノードを直している。拡張記法を入れるなら、自前の変換器に替える。

- 変換 API は拡張記法を知らない。印に置き換えて送り、戻ってから差し替える処理が、インラインの装飾では段落の中の TEXT の分割まで追うことになる
- 今のコードは変換 API の癖の後始末が多い（コードブロック末尾の改行、入れ子リスト末尾の改行、インラインコードの消失、30,000 字の分割）
- push はすでに画像・空段落・控えのノードを自前で組み立てて送っており、Blog API は手で作ったノード（`id: ""`）を受け付けている
- 対象は記事で使う範囲（見出し・段落・2階層までのリスト・引用・区切り線・コードブロック・画像・埋め込み）に限られる

自前にすると、pull の検算（上記）がネットワーク無しで回る。テストもオフラインで書ける。

代わりに、変換 API が持っていた「Wix 公式の解釈」を失う。差は段階2の検算（既存の控え JSON での往復）で洗い出す。

### 置き場所

Markdown ⇔ Ricos の変換と拡張記法の解析は、`scripts/lib/wix-markdown.mjs`（新設）に1つにまとめる。

- `wix-sync.mjs` は API 呼び出し・状態・控えの照合を持ち、変換はこのモジュールを呼ぶ
- `render-preview.mjs`・`lint-draft.mjs`・`revise.mjs` は、拡張記法の解析だけをこのモジュールから使う

今は「Wix 画像をキャプションで割り当てる処理」が `wix-sync.mjs` と `render-preview.mjs` に重複しており、今回のずれも両方で起きる。1か所にまとめて、記法の追加が片方に漏れないようにする。

## 公開済み記事の更新

既定は、公開中の記事の下書きを API で直接置き換えること（著者の判断 20261107）。試しの非公開の下書きは作らない。

この既定が安全なのは、次の2つが成り立つため。

- 置き換える前に、記事が非公開の複製 `[複製 {yyyymmdd}] {タイトル}` として Wix に残り、JSON も `wix-snapshots/` に残る
- 置き換わるのは下書き（未公開の変更）だけで、公開版は著者が Wix の画面で公開するまで変わらない

### 既定の手順

1. **下書きを pull する**: `pull <記事>`。同期時点を Wix の現在に揃え、画像の幅などを控える。結び付いていなければ、先に `link <記事> <postId> --relink`
2. **直す**: `/revise` の show → 著者の採否 → apply で、本文ファイルを直す
3. **点検する**: `push <本文> --update --allow-published --dry-run` で、落ちる装飾と画像のずれが無いかを見る（下記）
4. **著者の承認を得て送る**: `push <本文> --update --allow-published`
5. **公開は著者**: 編集画面の URL を返す。Wix の画面で確かめて公開するのは著者

### スキル間の食い違いを揃える

今は2つのスキルが逆のことを書いている。

- `revise` の「書き戻す」: 「公開済み記事なら著者が Wix の画面で行う」
- `wix-sync` の「公開済みの記事を書き直す」: API で下書きを置き換える手順を案内している

既定を wix-sync 側にまとめる。手順の正本は wix-sync の SKILL.md に置き、revise は「公開済み記事も、著者の承認後に `/wix-sync` で公開中の記事の下書きへ送る。公開は著者が Wix の画面で行う」と書いて参照するだけにする。wix-sync の節の名前は「公開済みの記事を更新する」に改め、「書き直す（旧記事を新しい本文に差し替える）」と「推敲を反映する」を同じ手順で扱う。

この揃えは記法の改修を待たずに入れられる。[段階0](#移行の手順)に含める。

### 前提が満たされるまでの運用

既定が無確認で成り立つ前提は、往復で装飾と画像が落ちないこと。具体的には、[段階1](#移行の手順)（画像を ID で書く）と[段階3](#移行の手順)（変えていない段落を控えのまま送る）が入っていること。それまでは次のように運用する。

1. dry-run の点検を必ず通す。段階0で、dry-run に「直前の pull の控えと比べて減る装飾と画像」の報告を足す。比べるのは、COLOR・UNDERLINE・BOLD・ITALIC の数、画像の Media ID の並び、画像の幅
2. 減るものが無ければ、そのまま承認を取って送る
3. 減るものがあれば、その一覧を承認の時に著者へ示す。送った後、減った装飾を下書きの JSON に API で足し直す（今回の後処理と同じ）。足し直しも Wix への書き込みなので、著者の承認を得てから行う
4. 画像の並びがずれる場合は送らない。旧記法のキャプション割り当てが原因なので、本文の該当箇所を直してから点検をやり直す

段階3が入った後は、3 の足し直しが要らなくなる。点検は残し、減るものがあれば止まる安全網として使う。

## 移行の手順

各段階は単独で入れられ、前の段階の記事をそのまま通す。順番は、公開済み記事を直接置き換える既定を安全にするものを先に置く（段階0〜3）。記法を増やすのはその後（段階4〜5）。

Wix への書き込みが要る確かめは、各段階の最後に著者の承認を得て行う。既定の手順に合わせ、実際に更新する記事の下書きで行ってよい（置き換え前の複製が残り、公開版は変わらないため）。新規の記法（色・埋め込み）を初めて送る確かめだけは、公開中の記事に混ぜず、テスト用の下書きで行う。

1. **段階0: つなぎの修正と手順の統一**。次の3つを入れる
   - PR #13（画像の幅の控え）をマージする。幅の控え `images[].container` は段階1で `{width=...}` の属性に移し、その時点で `wix.json` 側の控えは読むだけにする
   - dry-run に「直前の pull の控えと比べて減る装飾と画像」の報告を足す（[前提が満たされるまでの運用](#前提が満たされるまでの運用)）
   - revise と wix-sync の公開済み記事の手順を、wix-sync 側の既定にまとめる
2. **段階1: 画像を ID で書く**（問題3）。pull が `![cap](wix:ID "cap"){width=...}` を書く。push は新旧どちらも受ける。旧記法で同じキャプション（空を含む）の未使用画像が2つ以上残る場合は、推測で割り当てず止めて pull し直しを求める。ローカル画像にも `{width=...}` を書けるようにし、`images[].container` の控えはこの属性に移す
3. **段階2: 自前の変換器と往復の検算**。`scripts/lib/wix-markdown.mjs` を作り、`roundtrip <控え JSON>` で手元の `wix-snapshots/*.json` を全件往復させる。差が出たノードの種類を一覧にし、直すか控えに回すかを決める。この段階では記法は増やさない
4. **段階3: 落ちる段落の控え**（問題1の安全網）。pull の検算と `blocks` の控え、push の照合と停止。ここまで入れば、公開済み記事の直接の置き換えで、送った後の足し直しが要らなくなる
5. **段階4: インラインの記法**（問題1・2）。`{.accent}`・`{.u}`・`{color=...}`、リンクの下線。プレビューと lint を同時に対応させる
6. **段階5: 埋め込みの記法**（問題2）。`::x`・`::html{id}`。旧印 `<!-- Wixのノード: HTML #n -->` は push で読めるまま残し、次の pull で新記法に置き換わる
7. **段階6: スキルの文書**。wix-sync・article・revise の SKILL.md と references を更新する

既存の記事は、次に pull した時点で新記法に置き換わる。`published/` の Markdown は、著者が推敲反映するときに揃えればよく、一括の書き換えはしない。

検算の素材（控え JSON）は `output/` にあり、commit しない。リポに置くテストは、ダミーの文言と ID で作った小さな JSON に限る。

## 未検証の前提

いずれも段階2〜5の中で確かめる。Wix への書き込みが要るものは、著者の承認を得てテスト用の下書きで行う。

- **COLOR を手で付けたノードを Blog API が受け付け、編集画面と公開ページで同じ色に出るか**。pull で見えた形（`{ type: "COLOR", colorData: { foreground: "#E65100" } }`）をそのまま送る想定。未確認
- **最小限の X 埋め込み HTML が表示されるか**。`<blockquote class="twitter-tweet"><a href="URL"></a></blockquote>` と widgets.js だけで、Wix の HTML ノードがポストを描くか。未確認。描かない場合は X の oEmbed（`publish.twitter.com/oembed`）で HTML を取る。取得は Web 取得の規範に従い、著者の承認を得てから行う
- **HTML ノードの高さ**。Wix は HTML ノードに高さの指定を持ち、同じ埋め込みでも控えによって 198 と 1045 のように違った。新規の埋め込みに妥当な既定値があるか、著者が Wix で調整して pull で取り込む運用にするか。未確認
- **自前の変換器が変換 API と同等のノードを作れるか**。push は既に画像・空段落で手作りのノードを送っており、受け付けは確認済み。段落・リスト・見出しも手作りにした時、編集画面で開き直して形が崩れないかは未確認
- **編集画面で開くと Wix がノードを正規化するか**（例: 太字の `fontWeightValue` を足す、リンクに下線を足す）。正規化されると次の pull で差に見える。段階2で、送った直後の pull と比べて確かめる
- **変換 API が HTML 入力で色を受け付けるか**。自前の変換器を採らない場合の代替案の前提。採る場合は不要

## 著者の判断が要る点

推奨を先に置く。

1. **正本は Markdown のまま、JSON は控えに留める**（推奨: このまま）。JSON を正本にすると lint・プレビュー・差分・公開層を作り直すことになる
2. **変換を自前に替える**（推奨: 替える）。拡張記法を足す前提なら、変換 API に印を通すより単純になる。代わりに Wix 公式の解釈を失う分は、段階2の往復の検算で埋める
3. **色の記法を名前（`{.accent}`）にする**（推奨: 名前）。色を変えるとき1か所で済み、本文が読みやすい。名前の無い色は `{color=#...}` で書ける
4. **公開層の Markdown に Wix の Media ID が載る**（推奨: 許す）。ID は公開ページの画像 URL にそのまま出ている値で、サイト ID や API キーではない。許さない場合は `wix.json` 側に別名を持たせるが、`published/` だけでは画像が辿れなくなる
5. **文字色の強調を lint で数えるか**（推奨: 数えて警告だけ出す）。太字は `boldMax: 0` で抑えている。色の強調も同じ「強調の多用」に当たりうるが、公開記事での使用数を計測していないので、閾値は計測してから決める
6. **AI が書く draft.md に装飾を入れない**（推奨: 入れない）。色・下線は著者の表現の判断で、AI が先回りして置くと著者の文体を均す側に働く
7. **段階3までの間、落ちた装飾を送った後に API で足し直す**（推奨: 足し直す。どの装飾を足すかを承認の時に示す）。代わりに著者が Wix の編集画面で付け直す案もあるが、今回のように6か所あると手間が大きい。足し直しの処理は段階3で要らなくなるので、使い捨ての手順として wix-sync の本体には入れない

公開済み記事を直接置き換える既定そのものは、著者が 20261107 に決めた。この設計ではその前提で手順と順番を組んでおり、判断点には含めない。
