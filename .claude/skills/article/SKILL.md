# 記事づくり

著者と対話しながら1本の記事を **核 → 掘る → 組む → 書く** の順で作る。成果物は `output/{yyyymmdd}_$0/` に置き、以降 `$OUTPUT_DIR` はこのディレクトリを指す。

引数は2つとも任意。1つ目がテーマ（ディレクトリ名の後半）、2つ目が工程（`core` / `deepen` / `outline` / `write` / `map`）。日付プレフィックス付きのフォルダ名がそのまま渡されたらそれを使う。既存フォルダがあれば新規に作らず、そこへ書く。テーマが渡されていない時は `output/` の既存ディレクトリと著者の発言から決め、新規なら実行日を `{yyyymmdd}` に使う。

工程の遷移は同じ会話の中で進む。工程ごとにこのスキルを起動し直さない。

## 不変条件（全工程に効く）

1. **core.md が北極星**。どの工程でも最初に読む。承認後の core.md を AI は書き換えない。改訂は著者が「変える」と言った時だけ行い、末尾に `改訂: {yyyymmdd} {何を変えたか1行}` を追記する
2. **問いの規律**。著者に返す問いは、core.md のどの行（問い／読者／読後／動機／現在地）に効くかを名指しする。名指しできない問いは thinking.md の「駐車場」へ書き、著者には出さない。1ターンに返す問いは最大3件、対話では1度に1問ずつ
3. **本筋の書き換え禁止**。thinking.md のスコープや主張を AI が言い換える時は `[AI整理]` を付け、core.md の「問い」行と矛盾しないことを確認する。矛盾するなら著者に「核を変えるか」を聞く。これは問いの規律の例外で、いつ出してもよい
4. **調査は pull**。AI は自発的に Web 取得・調査サブエージェントを走らせない。特定の主張に裏付けが要る時に著者へ提案し、承認を得てから実行する。結果は references.md に1行で控え、raw は `$OUTPUT_DIR/references/` に置く
5. **鎧より主題**。想定反論の先回りは thinking.md 本文に足さず駐車場へ送る。反論への答えが主題を深める時だけ本文に置く
6. **真正性 > 網羅**。著者固有の論点（体験・立場・固有の判断）は AI が埋めない。`[AI案・要確認]` で仮置きして著者に返す。確信で埋めた偽の著者声は空欄より悪い

## 起動時の振る舞い

起動したら、まず次を読む（無ければ「無い」と分かればよい）。

- `$OUTPUT_DIR/core.md`
- `$OUTPUT_DIR/thinking.md` の「スコープ」節と「未決」節
- `$OUTPUT_DIR/map.html` の有無

そのうえで **現在地を3行で報告し、問いは1つだけ返す**。

```
核: {core.md の問い（1行）／未作成なら「未作成」}
進捗: {掘った論点 N 件／構成の有無／ドラフトの有無}
未決: {thinking.md の未決から1件。無ければ「なし」}
```

引き継ぎ文書（handoff.md 等）は作らない。状態はファイルが持つ。長い要約を返さない。

## 現在地の判定

2つ目の引数があればそれを工程にする。無ければファイルの有無と著者の発言で決める。

| 状態 | 工程 |
|---|---|
| core.md が無い（brief.md だけがある旧記事を含む） | 核 |
| core.md があり thinking.md が無い／著者が掘りたいと言う | 掘る |
| thinking.md があり、著者が構成を固めたいと言う | 組む（任意） |
| 著者が書くと言う | 書く |
| 2つ目の引数が `map` | 地図の再生成だけを行う |

旧記事（brief.md があり core.md が無い）は、brief.md と thinking.md の `[著者回答]` から core.md を起草して著者に承認を求める。brief.md は削除せず、内容は thinking.md へ吸収した旨を著者に伝える。

## 工程1: 核

対話で5行を起草し、著者の承認を得て `$OUTPUT_DIR/core.md` に書く。**AI が起草してよいが、文言を承認するのは著者**。承認が取れるまで次の工程に進まない。

```markdown
# 核: {タイトル案（仮）}

- 問い: {この記事が答えようとする、著者自身の問い。1文}
- 読者: {誰に向けて。1文}
- 読後: {読者に何が変わってほしいか。1文}
- 動機: {なぜ今書くのか。1文}
- 現在地: {答えは出ている／出ていない。1文}

承認: {yyyymmdd}
```

- 5行・各1文。各行は 120 字以内に収める
- 参考 URL が対話で出たら references.md に1行（タイトル・URL・一行要旨）で控える。本文の取得は掘る工程で必要になった時に行う（不変条件4）
- 承認直後に地図を初回生成する

## 工程2: 掘る

発散（横に広げる）と深掘り（縦に厚くする）を1つの対話で行い、`$OUTPUT_DIR/thinking.md` を作る・更新する。**掘ることに専念し、記事の見出し構成は設計しない**。

詳細な手順・問いの例・thinking.md のテンプレートは [references/phase-deepen.md](references/phase-deepen.md) を読む。

要点だけ再掲する。

- 深掘りに入る前にスコープを1往復で絞る。深掘りリストは3〜5点。取捨は「本質的」4条件（phase-deepen.md）で行う
- thinking.md を更新するたび、未決の問いを最大3件に絞り、各件に効く core 行を付す
- 掘る対話がひと段落したら地図を更新する
- 叩くのは著者が呼んだ時だけ。**critique は自動実行せず、提案に留める**（「主張を叩いておきますか」の一言）。著者が「叩いて」「反論ある？」「穴を見て」と言ったら隔離レビューを呼ぶ
- 戻ってきた指摘の採否にも「本質的」4条件を当てる。鎧を増やすだけの指摘は駐車場へ

## 工程3: 組む（任意）

thinking.md の主張と参考資料から、見出し構成・展開順序・資料接続を著者と対話で設計し `$OUTPUT_DIR/outline.md` に書く。

詳細な手順と outline.md のテンプレートは [references/phase-outline.md](references/phase-outline.md) を読む。

- **何を・どの順で語りたいかは著者の思想が要る**。いきなり構成案を書き出さず、著者の語りたい筋を先に聞く
- 著者の言う順序をそのまま清書しない。読者が迷子になる箇所・payoff が遠すぎる箇所・重複は指摘し、別案を提案する（採否は著者）
- outline.md 確定後に地図を更新し、隔離レビューの drift を提案する

この工程は飛ばしてよい。飛ばす場合は書く工程で thinking.md を直接の設計図にする。

## 工程4: 書く

`$OUTPUT_DIR/draft.md` を書き、圧縮・機械 lint・点検を通してから著者と磨きこむ。

詳細な執筆規範・採否基準・完了時の案内は [references/phase-write.md](references/phase-write.md) を読む。文体の正本は [references/voice-style.md](references/voice-style.md)、緩急の規範は [references/cognitive-rhythm.md](references/cognitive-rhythm.md)。

**内部の呼び出し順**（著者はこの順序を意識しなくてよい）:

1. draft.md を生成する（core.md 必須。無ければ工程1へ戻す）
2. 圧縮パスを回す（`tighten-draft`）
3. 機械 lint を回す（`node scripts/lint-draft.mjs $OUTPUT_DIR/draft.md`）。NG がゼロになるまで直す（最大3周）
4. 自己レビュー（lint では見えないものだけ読み返す）
5. 読者シミュレーションを回す（隔離レビューの `readers`）
6. 段階間ドリフトを点検する（隔離レビューの `drift draft`）
7. 指摘を反映して著者と磨きこむ。反映で本文が膨らんだら 2 に戻る
8. 空の `$OUTPUT_DIR/draft_user.md` を作る（既にあればスキップ）

著者に返すのは、本文へのパスと3行の要約（全体の流れ／lint の残件と直さなかった理由／フィードバックがほしい箇所）。全文を会話に貼らない。

## 地図の更新

`$OUTPUT_DIR/map.html` は計画の見取り図であり、**「この設計で書き始めてよいか」を著者が一目で判断するための合意ゲート**。抽出規則・テンプレートの使い方・検算は [references/map-spec.md](references/map-spec.md) を読む。生成は隔離せず、この対話の中で行う。

更新のタイミング:

| きっかけ | 扱い |
|---|---|
| core.md の承認直後 | 自動で生成する |
| thinking.md のスコープ確定後 | 自動で更新する |
| outline.md の確定後 | 自動で更新する |
| 著者が方針転換を口にした後 | 「地図を更新しますか」と提案する |
| 著者が「地図」「全体像」「俯瞰したい」と言った時 | 更新して返す |

- 正本は Markdown 側（core.md / thinking.md / outline.md）。HTML は一方向の写像で、手で直すと乖離する
- `map.html` は最新が正。世代を `map_NN.html` として溜めない
- Artifact ツールが使える環境では map.html を private Artifact として公開し、**同じファイルパスで再デプロイして URL を固定する**。使えない環境では `$OUTPUT_DIR/map.html` を開くよう案内する
- **著者に返すのは「地図: {URL またはパス}」と変更点1〜2行だけ**。地図の内容を会話に貼らない

## 隔離レビューの呼び出し

叩く・点検する仕事は隔離コンテキストへ出す。`Skill` ツールで `review` を起動し、引数を `"{テーマ} {lens} {対象}"` の形で渡す。lens は `critique` / `drift` / `readers` / `author` の4種。

| lens | 対象 | いつ |
|---|---|---|
| `critique` | thinking.md | 著者が「叩いて」と言った時だけ（提案はしてよい） |
| `drift outline` | outline.md | outline.md 確定後に提案する |
| `drift draft` | draft.md | 書く工程の既定 |
| `readers` | draft.md | 書く工程の既定 |
| `author` | draft_user.md | 著者が「下書きを見て」と言った時 |

呼び方の例: `Skill` ツールで `review` を引数 `{テーマ} critique` で起動する。drift は `{テーマ} drift draft`、author は `{テーマ} author`。ドラフトの圧縮は `Skill` ツールで `tighten-draft` を引数 `{テーマ}` で起動する。`{テーマ}` には `$OUTPUT_DIR` の決定に使ったテーマ（日付プレフィックス付きのフォルダ名でもよい）を渡す。

戻ってきた指摘は3件まで。各指摘に効く core 行が付いている。反映する時は修正ごとに「この修正は主題を深めるか、鎧を増やすだけか」を問い、後者は本文に入れず ℹ️ 引き継ぎメモへ送る（不変条件5）。
