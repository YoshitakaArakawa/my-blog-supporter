# 記事づくり

著者と対話しながら1本の記事を **核 → 掘る → 組む → 書く** の順で作る。工程の遷移は同じ会話の中で進む。工程ごとにこのスキルを起動し直さない。

引数: `$ARGUMENTS`（1つ目がテーマ、2つ目が工程 `core` / `deepen` / `outline` / `write` / `map`。どちらも任意）

成果物は `output/{yyyymmdd}_{テーマ}/` に置き、以降 `$OUTPUT_DIR` はこのディレクトリを指す。既存フォルダがあれば新規に作らずそこへ書く（テーマに日付プレフィックスが付いていればそのまま使う）。テーマが渡されていない時は `output/` の既存ディレクトリと著者の発言から決め、新規なら実行日を `{yyyymmdd}` に使う。

## 不変条件（全工程に効く）

1. **core.md が北極星**。どの工程でも最初に読む。承認後の core.md を AI は書き換えない。改訂は著者が「変える」と言った時だけ行い、末尾に `改訂: {yyyymmdd} {何を変えたか1行}` を追記する
2. **問いの規律**。著者に返す問いは、core.md のどの行（問い／読者／読後／動機／現在地）に効くかを名指しする。名指しできない問いは thinking.md の「駐車場」へ書き、著者には出さない。thinking.md の未決節に残す問いは最大3件。会話で著者に返すのは1度に1問
3. **本筋の書き換え禁止**。thinking.md のスコープや主張を AI が言い換える時は `[AI整理]` を付け、core.md の「問い」行と矛盾しないことを確認する。矛盾するなら著者に「核を変えるか」を聞く。これは問いの規律の例外で、いつ出してもよい
4. **調査は pull**。AI は自発的に Web 取得・調査サブエージェントを走らせない。特定の主張に裏付けが要る時に著者へ提案し、承認を得てから実行する。結果は references.md に1行で控え、raw は `$OUTPUT_DIR/references/` に置く
5. **鎧より主題**。想定反論の先回りは thinking.md 本文に足さず駐車場へ送る。反論への答えが主題を深める時だけ本文に置く
6. **真正性 > 網羅**。著者固有の論点（体験・立場・固有の判断）は AI が埋めない。`[AI案・要確認]` で仮置きして著者に返す。確信で埋めた偽の著者声は空欄より悪い
7. **叩くのは著者が呼んだ時だけ**。critique を自動で走らせず、提案に留める

## 起動と現在地

起動したら、まず `$OUTPUT_DIR/core.md`・`$OUTPUT_DIR/thinking.md` の「スコープ」節と「未決」節・`$OUTPUT_DIR/map.html` の有無を読む（無ければ「無い」と分かればよい）。そのうえで **現在地を3行（核: core.md の問い／進捗: 掘った論点数・構成・ドラフトの有無／未決: 未決から1件）で報告し、問いは1つだけ返す**。引き継ぎ文書（handoff.md 等）は作らない。状態はファイルが持つ。長い要約を返さない。

工程は2つ目の引数があればそれにする。無ければ次で決める。

- core.md が無ければ **核**。あって thinking.md が無い、または著者が掘りたいと言えば **掘る**
- 著者が構成を固めたいと言えば **組む**（任意）、書くと言えば **書く**
- 2つ目の引数が `map` なら地図の再生成だけを行う

## 隔離レビューの呼び出し

叩く・点検する仕事は隔離コンテキストへ出す。`Skill` ツールで `review` を起動し、引数を `"{テーマ} {lens} {対象}"` の形で渡す。`{テーマ}` には `$OUTPUT_DIR` の決定に使ったテーマ（日付プレフィックス付きのフォルダ名でもよい）を渡す。

| lens | 対象 | いつ |
|---|---|---|
| `critique` | thinking.md | 著者が「叩いて」と言った時だけ（提案はしてよい） |
| `drift outline` | outline.md | outline.md 確定後に提案する |
| `drift draft` | draft.md | 書く工程の既定 |
| `readers` | draft.md | 書く工程の既定 |
| `author` | draft_user.md | 著者が「下書きを見て」と言った時 |

戻ってきた指摘は3件まで。各指摘に効く core 行が付いている。反映する時は修正ごとに「この修正は主題を深めるか、鎧を増やすだけか」を問い、後者は本文に入れず ℹ️ 引き継ぎメモへ送る（不変条件5）。

## 他スキルへの受け渡し

| 著者の発言 | 渡す先 |
|---|---|
| 「短くして」「削って」 | `tighten-draft`（`Skill` ツールで引数 `{テーマ}`） |
| 「Wix から取り込んで」 | `/import-wix-draft` → 続けて `review` の `author` |
| 「公開した。比べて」＋URL | `/compare-drafts` |
| 「図を入れたい」 | `/illustrate` |
| Web 取得が要る（SPA・要ログイン） | `/fetch-page`（不変条件4の承認を得てから） |
| 「公開する」 | `/publish-article`（著者が自分で起動する） |

## 工程1: 核

対話で5行を起草し、著者の承認を得て `$OUTPUT_DIR/core.md` に書く。**AI が起草してよいが、文言を承認するのは著者**。承認が取れるまで次の工程に進まない。

- 5行・各1文・各行 120 字以内。骨格は [templates/core-template.md](templates/core-template.md) を読む
- 参考 URL が対話で出たら references.md に1行（タイトル・URL・一行要旨）で控える。本文の取得は掘る工程で必要になった時に行う（不変条件4）

## 工程2: 掘る

発散（横に広げる）と深掘り（縦に厚くする）を1つの対話で行い、`$OUTPUT_DIR/thinking.md` を作る・更新する。**掘ることに専念し、記事の見出し構成は設計しない**。詳細な手順・問いの例・thinking.md のテンプレートは [references/phase-deepen.md](references/phase-deepen.md) を読む。

- critique は提案に留める（「主張を叩いておきますか」の一言）。著者が「叩いて」「反論ある？」「穴を見て」と言ったら隔離レビューを呼ぶ（不変条件7）
- 戻ってきた指摘の採否にも「本質的」4条件（phase-deepen.md）を当てる。鎧を増やすだけの指摘は駐車場へ

## 工程3: 組む（任意）

thinking.md の主張と参考資料から、見出し構成・展開順序・資料接続を著者と対話で設計し `$OUTPUT_DIR/outline.md` に書く。詳細な手順と outline.md のテンプレートは [references/phase-outline.md](references/phase-outline.md) を読む。

**何を・どの順で語りたいかは著者の思想が要る**。いきなり構成案を書き出さず、著者の語りたい筋を先に聞く。確定後に地図を更新し、隔離レビューの `drift outline` を提案する。

この工程は飛ばしてよい。飛ばす場合は書く工程で thinking.md を直接の設計図にする。

## 工程4: 書く

`$OUTPUT_DIR/draft.md` を書き、圧縮・機械 lint・点検を通してから著者と磨きこむ。詳細な執筆規範・採否基準・完了時の案内は [references/phase-write.md](references/phase-write.md) を読む。文体の正本は [references/voice-style.md](references/voice-style.md)、緩急の規範は [references/cognitive-rhythm.md](references/cognitive-rhythm.md)。

**内部の呼び出し順**（著者はこの順序を意識しなくてよい）: draft.md の生成（core.md 必須。無ければ工程1へ戻す）→ 圧縮パス（`tighten-draft`）→ 機械 lint（`node scripts/lint-draft.mjs $OUTPUT_DIR/draft.md`。NG がゼロになるまで最大3周）→ 自己レビュー → 読者シミュレーション（`readers`）→ 段階間ドリフト点検（`drift draft`）→ 指摘を反映して著者と磨きこむ（膨らんだら圧縮パスへ戻る）→ 空の `$OUTPUT_DIR/draft_user.md` を作る。

著者に返すのは、本文へのパスと3行の要約（全体の流れ／lint の残件と直さなかった理由／フィードバックがほしい箇所）。全文を会話に貼らない。

## 地図の更新

`$OUTPUT_DIR/map.html` は計画の見取り図であり、**「この設計で書き始めてよいか」を著者が一目で判断するための合意ゲート**。抽出結果を `$OUTPUT_DIR/map.json` に書き、`node scripts/render-map.mjs $OUTPUT_DIR/map.json` で map.html を生成する（詳細は [references/map-spec.md](references/map-spec.md)）。生成は隔離せず、この対話の中で行う。

| きっかけ | 扱い |
|---|---|
| core.md の承認直後 | 自動で生成する |
| thinking.md のスコープ確定後 | 自動で更新する |
| outline.md の確定後 | 自動で更新する |
| 著者が方針転換を口にした後 | 「地図を更新しますか」と提案する |
| 著者が「地図」「全体像」「俯瞰したい」と言った時 | 更新して返す |

**著者に返すのは「地図: {URL またはパス}」と変更点1〜2行だけ**。地図の内容を会話に貼らない。
