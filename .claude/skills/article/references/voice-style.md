# 著者の文体・語り口メモ

著者: Yoshitaka Arakawa - BI Developer / Tableau Trainer

> **使い方**: 効く順に並べてある。**0. 数値仕様** は `node scripts/lint-draft.mjs` が機械で判定する。**1. 実例** は公開記事の抜粋で、ルールより先に読んで文の手触りを掴む。**2〜3 のルール** は実例で伝わらない判断を補う。ルール 1〜16 は「従うべき型」、17〜23 は「AI が既定で出す傾向への対抗ガイド」。

## 0. 数値仕様（機械ゲートの閾値）

公開記事10本（2024〜2026）で一貫していた指標。AI 版はこの全てで公開版から外れていた（分量 1.4〜1.9 倍、段落 2.7〜3.7 文、「」2〜4 倍）。

| 指標 | 仕様 | 根拠（公開記事の実測） |
|---|---|---|
| 段落あたりの文数 | **1〜2 文**。3 文目で改段。括弧の補足は独立段落 | 1.1〜1.7 文 |
| 本文字数 | **4,000〜7,000 字** | 5.3k〜7.5k |
| 一文の長さ | 140 字以下。平均 50 字前後 | 42〜60 字 |
| 「」の個数 | 本文全体で **25 個以下**。概念名は初出のみ囲う | 8〜36 |
| 大見出し `##` | 4〜5 本 | 4〜5 |
| 小見出し `###` | 原則 0。余談を立てる時のみ 1 | 0〜2 |
| 太字 `**` | 0 | 0（リスト見出しに残る例が数件） |
| ダッシュ（— ― ――） | 0 | 0 |
| 造語・キーフレーズの反復 | 本文 5 回まで。章題には使わない | 「開いた土台」×12 が AI 側の反例 |
| 英文引用 | 3 文まで。英語ラベル（fail-open 等）は 0 | 0〜2 |
| 冒頭 | 「この記事では〜」の宣言、または「〜してきました」の体験 | 宣言 7/10、体験 2/10 |
| 冒頭の参考資料ブロック・固定ヘッダ | 置かない | 0/10 |
| 結び `## 最後に` | 18 文以内。読者への問い返しなし | 4〜18 文、問い返し 0/10 |

**禁止句**（`scripts/draft-lint.config.json` が正）。AI 版に実測で出て、公開版にほぼ出ない語:

- 保険・誠実さの演出: 「誤解されたくないので」「念のため補足すると」「公平に見ておきたい」「正直に書くと」「〜は認めます」「これは論証ではありません」「まだ見つけられていません」
- 口癖: 文頭の「だから」（「だからこそ」は可）・「ただ、」、「んです／なんですよね」、「たぶん」、かな書きの「たとえば」「いちばん」
- 結びの定型: 「この記事を書いた動機は」「最後に問いを残します／返します」「また考えが変わったら書いてみます」
- 章間の道案内: 「ここまでは〜の話でした」「ここから少し」「次は〜の話に入ります」
- 空句: 「重要なのは」「正面から」「不可欠」「掘り下げる」「〜の観点から」「非常に」
- 英語ラベル: fail-open / fail-safe / first-class / opt-out / capability を日本語で言い直す

**推奨語彙**（公開記事にあり AI 版に無い、著者の指紋）: 「〜かなと。」「〜のでは、と。」「まぁ」「...」「！」「例えば」（漢字）「一方で」「ただし」「ということで」（章の結び）「好き」「面白い」

## 1. 実例（公開記事からの抜粋）

ルールより先にこれを読む。各例は「何を見るか」を1行添える。

### 実例1: 導入は宣言＋スコープ＋動機で 4 段落

> この記事では、Tableau MCPやAI Agentにある程度向き合ってきたからこそ感じた、Tableau MCPを組織展開する際の懸念について書きます。
>
> 主には複数部署が同居するようなTableau Server環境を念頭に書きますが、懸念自体はTableau ServerとTableau Cloudの両方に、環境の規模感に関係なく当てはまるものだと思っています。
>
> 本記事の意図は、あくまでも「仕様を理解しない状態でTableau MCPを使うことにより、普及が止まることを防ぎたい」ことです。
>
> 推進したい立場の人間が懸念を書くのはTableau MCPに水を差すようで気が引けるのですが、いずれ皆が気づくであろう論点を、前倒しで一度言葉にしておきたいと思いました。

見るところ: 1 段落 1〜2 文。参考リンクも固定ヘッダも無い。動機（水を差すようで気が引ける）が 1 文で入る。

### 実例2: 思考段落は短く、括弧で脱線し、「かなと。」で置く

> 端的かつTableauユーザー向けに限って言えば、今までは「Tableauでこんな面白いことが出来たら、もっと楽しいですよね！」でゴリ押し出来たものの、AI文脈だと「今までやってきたことをAI Agentに任せて、自分たちの今の仕事を無くしたいですよね！」というような話が避けて通れないかなと。
>
> （まぁ自分のTableauブログや発信も、自分と他者の専門性を希釈してきた部分はあると思いますが、AI Agent関連ではもっと激しい話になってしまうので...）
>
> ということで、着地がどのようになるか冒頭執筆時点では全く分かりませんが、自分の楽しみと興奮、そして人への勧め方が分からんという気持ちを書いてみようと思います。

見るところ: 体温は「まぁ」「...」「分からん」で出す。「んです」「だから」は使わない。括弧の脱線が独立段落。

### 実例3: 反論は認めたまま、答えを出さずに立場だけ書く

> 端的に言えば、現在の自分（と、もしかしたら他者）のキャリア上の墓穴をせっせと掘っているのと同義なんじゃないか、と思っています。というより実際にそうですよね。
>
> 「労働者目線で合理的に考えたら、AI Agentを頑張る理由って無いんじゃないか？」という意見には、理解と共感を覚えます。正直まちがっていないと思いますし、このモチベーション設計で成功している組織や人がいれば、切に知りたいです。

見るところ: 救済ロジックを組まない。「専門性は上の層へ移る」式の反論回収を AI 版は 9 段積んだが、著者は 2 段落で認めて次へ進む。

### 実例4: 引用素材は 1 段の受け止めで読者に渡す

> 加えて、こちらの図も好きですね。
>
> アドホックか定点観察的か、探索的かシグナル探知的かという2軸で切り分けた際に、どのアプローチを取るべきかというフレームワークです。
>
> 現在ではAI Agentも含めてデータ利用体験を設計することがTableauからも推奨され、また判断軸/判断の材料も提示されている。可視化周辺だけではない、総合格闘技のような戦い方が求められているようで、自分は面白く受け止めています。
> （まぁこれは純粋なAI Agent推奨だけでなく、Tableau NextやTableau Agentの文脈もあると思いますが）

見るところ: 「好き」「面白く受け止めている」で止める。多段解釈や他主張への接続をしない。

### 実例5: 事実・年表・並列は箇条書き、思考は散文

> ここ2年ほどでTableauデータソースが、Tableau x AIにおける主要な要素になっていると認識していることが動機です。
>
> - 2024年：Tableau Pulseの登場。これはデータソース上の指標を（ワークブックを介さず）自然言語で読ませてくれる
> - 2025年：VizQL Data Service API で Published Data Source を API 経由で直接クエリできるようになった。
> - 2026年：Tableau Conference 2026 では「Agentic Analytics Platform」という構想が打ち出された。

見るところ: AI 版は年表を散文に溶かし、概念の分類を箇条書きにする。著者は逆。

### 実例6: 結びは短い割り切り、または「ということで〜でした」

> 身も蓋もない話をすると、どうせこの先、誰かが既存の専門性を壊していくと思います。Tableauやデータ活用の領域でそれが起きるなら、その領域に愛がある人間が率先してやった方がいい。自分はそう考えています。
>
> （中略）
>
> この体験談が役に立つようであれば嬉しいです。それでは！

> ということで、Agentic Analytics PlatformとしてのTableauを見据えた、実験的アイデアの共有でした。
>
> （中略）
>
> 質問などありましたら、XかLinkedinまでお願いします。
>
> よいAgentic Analyticsを！

見るところ: 動機の再掲・読者への問い返し・続編予告が無い。

### 実例7: AI 版の典型と、著者水準への直し方

| AI 版（避ける） | 著者水準（こう書く） |
|---|---|
| 正直に書くと、自分がいちばん気にしているのは事故です。 | 自分が一番気にしているのは事故です。 |
| 誤解されたくないので一文だけ補足すると、崩れるのは権限モデルではなく運用の前提です。 | （削除。反論への返しは ℹ️ メモへ） |
| 最後に1つ、問いを残します。あなたの組織はどのあたりに立っているでしょうか。 | もしこの懸念に共感してもらえたら、担当のTableauの中の人に、ぜひ一度この話を挙げてみてください。 |
| ここまでは、ほぼ祝福の話です。ここから少し、踏み込んだ話を。 | 一方で、 |
| 「開いた土台」（記事内 12 回、章題にも） | 初出で 1 回。以後は普通の語で言い換える |

## 2. 従うべき型（ルール 1〜16）

### 1. 一人称・基本トーン

- 一人称は「自分」（「私」「僕」は使わない）
- 敬体（〜です・〜ます）。敬度は柔らかい
- ヘッジは文体資産。「思います」「気がします」「かもしれません」は削らない。ただし語尾だけの連続は機械的に見えるので、次と混ぜる:
  - 引用止め: 「〜かなと。」「〜のでは、と。」
  - 括弧書きの自己訂正・脱線: 「（まぁ人間にとっても〜）」「（筆者の勘違いである可能性は、もちろん大いにありますが）」
  - 感情の直言: 「面白かったです」「楽しかったですね」「便利！」「好きです」
  - 余韻と軽口: 「...」「←」
- 体温を「んです」「なんですよね」「だから」で出さない。AI 版はこれで温度を代用し、著者は使わない

### 2. 強い断定を避ける

- 「〜と感じます」「〜かもしれません」「〜のように見えます」
- 分からないことは開示する: 「ちょっと良く分からないですね」「切に知りたいです」
- 「絶対」「必ず」は使わない
- 「正直に書くと」「正直なところ」の前置きは使わない（誠実さの演出になる）。「正直まちがっていない」のように評価語として使う分は可

### 3. 鉤括弧「」による強調

- 主張・重要フレーズ・概念名を「」で囲う。太字は使わない
- 本文全体で 25 個以下。概念名は初出だけ囲い、以後は囲わない。一般語（「設計」「窓口」）は囲わない

### 4. 読者への直接エンゲージ

- 問いかけ「〜でしょうか？」「〜ですよね？」、呼びかけ「ぜひ〜してみてください」
- 例: 「何ごとも『大したことない』人でも出来るなら、自分でも出来そうだって気がしませんか。」

### 5. 具体例で抽象を裏付ける

- 順序は **具体観察 → 抽象解釈**。現地で見たもの・固有名詞・セッション名・タイムスタンプから入る
- 補強は要約数値（「89%」「20年」）より、刺さった一次資料の原文引用。ただし英文引用は 3 文まで
- 例: Sample Superstore × 生成AI のロールプレイ、Tableau MCP のセットアップ、ダッシュボードの再現性運用

### 6. 遷移句

| 用途 | 使う | 使わない |
|---|---|---|
| 対比 | 「一方で」「ただし」 | 文頭の「ただ、」 |
| 例示 | 「例えば」（漢字） | 「たとえば」 |
| 帰結 | 「なので」「つまり」 | 文頭の「だから」 |
| 章の結び | 「ということで、〜でした」 | 「ここまでは〜、ここからは〜」 |
| 補足 | 「ちなみに」 | 「さらに」「また」「加えて」の連打 |

章間のロードマップ的提示はしない。読者は章タイトルから構造を読める。

### 7. 「否定→ただし」パターン

否定的事実を認めた上で価値を再評価する型。**自分が学んできた技術・姿勢の再評価、過去の自分の見方の修正**にだけ使う。製品や他者への批判→フォローには使わない（ルール 20）。

> 学んできたTableauの高度な技術は、そのうち使わなくなるかもしれない。
> ただし、その技術を必要とした背景や、その技術で解決してきた課題に関する経験や思考は、生成AIエージェントに応用させることができる。

### 8. 余談

- 本筋に組み込めない時だけ。散文に組み込めるなら組み込む。記事に余談が 1 つも無くて問題ない
- 置き場所は末尾。内容はメタ・後日譚（「Blog執筆 Agent に挿絵 Skill を足した」）が著者らしい。中盤の技術メモには使わない
- 本文に盛ると重くなる技術詳細・自分の実装手順は、余談か外部リンクに逃がす

### 9. 結論セクション「## 最後に」

- 必ず `## 最後に` で締める。18 文以内
- **既定の型**: 「ということで、〜でした」または「身も蓋もない話をすると〜」の短い宣言 → 分からない部分は分からないまま → 感情の一言 → CTA またはサインオフ
- サインオフ: 「質問などありましたら、XかLinkedinまでお願いします。それでは！」が基本。テーマ変奏（「よいAgentic Analyticsを！」）や省略形（「それでは！」のみ）も著者の実績。二重に付けない
- 使わない: 動機の再掲（「この記事を書いた動機は」）、読者への問い返し（「あなたは〜でしょうか」）、続編予告（「また考えが変わったら書いてみます」）、宿題の開示
- 感想記事は短い箇条書き集約（5 箇条程度の感想＋サインオフ）も可

### 10. 新概念の導入

- 教科書的網羅を避ける。「（簡単に）」「（自分の理解）」を見出しに添える
- 「と自分は理解しています」で私見を示す
- 便宜呼称（例: 「Tableau Classic」= Cloud/Server/Desktop/Prep の総称）は使い始める前に 1 文で定義する

### 11. フォーマット規約

- **段落**: 1〜2 文。3 文目で改段する。括弧の補足・脱線は独立段落にする。段落間は空行 1 つ
- **リスト**: 思考は散文、事実・年表・並列（機能名・動機 1/2）は箇条書き。概念の分類を箇条書きにしない
- **見出し**: `##` を主軸に 4〜5 本。`###` は余談のみ。`##` の前後に `---`
- **太字**: 使わない。リスト見出し・ステップ番号も太字にしない
- **冒頭ブロック**: 「参考資料」ブロック・「Tableau NOTE」固定ヘッダ・著者プロフィールは draft.md に入れない（Wix 側にある）
- **参考リンク**: 本文中の該当箇所に「参考：」「例えば○○のBlogから：」の短い導入＋タイトルの箇条書き、または「こちらの記事」の自然な言及で分散させる
- **画像**: 主張の直後に `<!-- 画像: {説明} -->`、画像下に補足説明
- **タイトル末尾**: 「(YYYY年MM月版)」を付けることがある

### 12. タイトル

- 既定は控えめな枠: 「〜の感想」「〜について」「〜の向き合い方 (YYYY年MM月版)」「〜する実験」「〜を考える」
- 引用符付きキーフレーズ・「だからこそ〜してほしい」型の要望前面・煽りは著者が明示した時だけ

### 13. 過去記事との接続

- 「以前○○という記事を書きましたが」と自然に言及し、リンクは本文の流れに埋める

### 14. 用語・語彙・表記

- カタカナ語を恐れない。「BIツール」「Tableauユーザー」を主語にすることが多い
- 表記辞書は `scripts/prh.yml` が正（AI Agent / VizQL Data Service / LinkedIn 等）。揺れに気づいたら prh.yml に追記する
- 和文と英単語の境界に半角スペースを入れない（「TableauはREST APIを叩く」）。英語フレーズ内部の語間スペースは残す
- 数量は算用数字（「2つ」「1つめ」）。熟語の漢数字（「一方」「一貫性」「唯一」）は残す
- ダッシュ（— ― ――）を使わない。補足は（）、言い換えは句点で二文に
- 中黒（・）を並列に使わない。並列は読点。固有名詞内部は可
- 英語ラベル（fail-open / first-class / opt-out / capability）で精密さを演出しない。一次資料に英語の固有概念名がある時だけ英語を使う

### 15. 著者のスタンス

- 活動の核は「再現性」と「ギャップを埋める」。「自分の特別性は不要、誰でも辿れる論理を整備したい」
- 「危機感を煽る」「驚かせる」論調は避ける
- ブログの目的: 世界で使われている技術を広める／Tableau とデータ可視化の日本語ドキュメントを増やす／学習内容を整理し言語化する

### 16. やらないこと

- 煽り、教科書的網羅、強断定、結論の一点収束、専門家ぶる、平板で無個性な文章

## 3. AI 的傾向への対抗ガイド（ルール 17〜23）

AI が既定で出す傾向を、公開版との差分（compare-drafts の蓄積）から特定したもの。「〜しすぎない」ではなく「既定でやらない」と読む。

### 17. 構造化のミニマリズム

- `##` は 4〜5 本。論点ごとに章を立てず、近接論点は同じ章にまとめる
- 章タイトルは短い問い・観察・宣言。見出しで節のオチを言い切らない
  - 良い例: 「Architectというキーワード」「ユーザー側の準備はあるか」
  - 避ける例: 「ただし○○を本気で受け取ると○○だけでは足りない」
- 並列の論点を明示する番号見出し（「動機1: 〜」「動機2: 〜」）は可
- `###` は余談のみ。技術詳細の小見出しを立てない

### 18. 抽象メタファーの使い捨て

- 造語・キーフレーズは本文 5 回まで。章題・章をまたぐ参照には使わない
- メタファーは具体観察の解釈として 1 回出すだけ。柱は具体観察と問いの連鎖

### 19. 冒頭設計

- **既定は宣言スタート**: 「この記事では〜について書きます」＋スコープ 1〜3 文＋執筆動機 1〜2 文。合計 3〜6 段落、600 字前後（実例1）
- **体験スタートは参加記のみ**: 「○○に参加・登壇してきました」（カンファレンス・イベントの感想記事）
- 年表・スコープ整理・前提の羅列で導入を重くしない。背景の時系列は本文の該当章へ送る
- 執筆動機は AI が core.md / thinking.md をもとに下書きする（著者は後から直す）。特定の瞬間の一次感情など AI が持たない素材だけを `> ✍️` の可視マーカーで残す

### 20. 主体性の方向

- 批判や課題提起は、外側（製品・組織・他者）ではなく自分・我々ユーザー側に向ける
- 「Tableau Classic の API-first 非対応」ではなく「我々ユーザー側のインプットや知識が Tableau に閉じていないか」

### 21. 固有名詞のリアリティ

- 現地で見た人名・セッション名・タイムスタンプを躊躇せず出す（「Beyond the Boundaries of Tableau (特に26:40から)」「Will さんのパート」）
- 敬称は「○○さん」

### 22. 保険・演出・空句を書かない

AI は「ちゃんと書いている感」を足すために、新情報を運ばない文を挿む。公開版はこれをほぼ全て削っていた。「0. 数値仕様」の禁止句がその一覧で、lint が検出する。

判定の原理は1つ: その文が更新するのは「状況」（対象世界の出来事・書き手の判断の状態）か、「文書」（この記事自身の見え方・進行）か。文書だけを更新する文は、禁止句リストに無い形でも削る。原理の詳細と点検手順は [cognitive-rhythm.md](cognitive-rhythm.md) を参照。

- 反論への返し・出典の性質開示は本文に置かず、ドラフト冒頭の ℹ️ 引き継ぎメモへ（「コメント欄で突かれたら返す用」）
- 「正直」「たぶん」「いちばん」「んです」は著者の口癖ではなく AI の口癖
- ヘッジ（「かもしれません」「思います」）と遷移句（「つまり」「一方で」「ただし」「ということで」）は対象外。削らない

### 23. 論証のミニマリズム

- 想定反論に救済ロジックを組まない。妥当な反論は「正直まちがっていない」と認めたまま立場だけ表明する（実例3）
- 1 つの章は 5 手で畳む。9 段の精密な論証を書かない
- 引用素材は 1 段の受け止めで読者に渡す（実例4）
- 1 つのアハ（気づき）を、権限の分解・追加引用・英文原文で過剰補強しない。同じ結論を日本語の平地で少ない引用で運ぶ
- 答えの出ない部分は出さないまま閉じてよい

## 記事の典型構造

```
タイトル（控えめな枠）
公開日ブロック
導入: 「この記事では〜」宣言 ＋ スコープ ＋ 動機（3〜6 段落）／参加記は体験スタート
      ↓
## 大セクション1（問い / 観察 / 短い宣言）
   事実・年表は箇条書き、思考は 1〜2 文の段落
      ↓
## 大セクション2（対比・別側面）
      ↓
## 大セクション3（射程拡張、または反論を認めたままの立場表明）
      ↓
## 最後に（短い割り切り → 分からないことは分からないまま → 感情の一言 → CTA／サインオフ）
   ### 余談（末尾のメタ・後日譚。無くてよい）
```

## 生成後の点検

機械で数えられるものは lint に任せ、LLM は判断が要るものだけ見る。

1. `node scripts/lint-draft.mjs $OUTPUT_DIR/draft.md` を実行し、NG をゼロにするまで直す（/article の書く工程の機械 lint）
2. lint では見えないものを読み返す:
   - 実例 2〜4 の手触りに近いか（体温は「まぁ」「...」「！」で出ているか、反論を認めたまま次へ進んでいるか、引用素材を 1 段で渡しているか）
   - 見出しが節のオチを言い切っていないか（ルール 17）
   - 批判の向きが我々ユーザー側になっているか（ルール 20）
   - 固有名詞・一次情報が抽象化されていないか（ルール 21）
   - 用語を途中で変えた場合、旧表現の残骸が無いか
