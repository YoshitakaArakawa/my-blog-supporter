# 組む工程

## 目次

- 入力
- 1. 構成の設計（著者との対話）
- 2. outline.md の生成
- 3. 確定後
- やらないこと

**何を・どの順で語るかの最終判断は著者が握る。** 展開順序・力点・どこで何を明かすかは thinking.md から一意には決まらない。一方で著者は掘る対話の全量を覚えていないため、AI が叩き台を先に出し、著者が並べ替え・削る形で組み立てる。著者の修正もそのまま受け入れず、読者が迷子になる箇所・payoff が遠すぎる箇所・重複は指摘する（最終判断は著者）。

この工程は任意。飛ばす場合は thinking.md が書く工程の設計図になる。

## 入力

- `$OUTPUT_DIR/core.md`（必須）
- `$OUTPUT_DIR/thinking.md`（必須。無ければ掘る工程へ戻す）
- `$OUTPUT_DIR/references.md`（あれば。資料接続の設計に使う）
- `$OUTPUT_DIR/review/critique_*.md` の最新（あれば。未対応の指摘が構成に反映されているか確認する）

参考資料は構成設計の前に中身を把握しておく。ローカル資料（`$OUTPUT_DIR/references/`）は Read で読む。URL の本文がまだ取れていない場合は、勝手に取得せず著者に「この資料は本文まで読んでおきますか」と提案し、承認後に取得する（不変条件4）。各資料の要点を、thinking.md のどの主張に、どのセクションで、どう接続するかまで考えてから対話に入る。

## 1. 構成の設計（著者との対話）

まず core.md と thinking.md（スコープ・各観点）から構成の叩き台を1案、会話に出す。outline.md にはまだ書かない。

- 各章に、根拠となる thinking.md の観点を添える。thinking.md に無い主張を構成の都合で足さない
- 並べた理由（読者が追える順序・payoff の位置）を1〜2行添える
- 代案は、順序の選択が core に効く時だけ1つに留める

著者の並べ替え・削除・追加を受けて、対話で構成を固める。叩き台と著者の修正の両方を次で検証し、**引っかかる点は指摘する**（採否は著者）。

- 各論点の展開順序は自然か。著者が語りたい筋と、読者が追える順序がずれていないか
- core.md の「問い」に答え、コアメッセージに収束しているか
- 読者が途中で迷子にならないか。最も難しいピーク／payoff が本筋の手前で遠すぎないか
- 各セクションの重み付け（ボリューム配分）は適切か
- 不要な要素を削ぎ落とせるか。同じ話の重複はないか
- critique で出た未対応の指摘が、構成のどこかで解消されているか

対話で筋が固まってから outline.md の生成に進む。指摘は一度に3件までにし、各指摘が core.md のどの行に効くかを名指しする。

## 2. outline.md の生成

outline.md は著者がレビューする中間成果物。**要点を構造的な箇条書き（入れ子可）で書き、スキャンしやすくする**。散文の段落で書かず、論点・対比・選択肢（例: (i)/(ii)、二軸、反証条件）は子箇条書きに分解して階層で見せる。

**箇条書きは「話す順の骨」であって最終本文の形ではない**。本文は書く工程で散文化する（内省エッセイの没入を箇条書きで平板化させないため）。この前提を outline.md 冒頭にも一文置く。

```markdown
# 記事構成: {記事タイトル案}

<!-- 以下の箇条書きは話す順の骨であり、最終本文の形ではない。本文は散文化する -->

## コアメッセージ
- {この記事の一番伝えたいこと}

## 読後の読者の状態
- {読者が読後どうなっていてほしいか。core.md の「読後」行と整合させる}

## 構成

### 導入: {見出し案}
展開する思考（話す順）:
- {要点1}
  - {補足・根拠・具体}
- {要点2}
素材:
- {使える具体例・エピソード・参考資料}

### 展開1: {見出し案}
展開する思考:
- {要点1}
  - {対比や選択肢は子箇条書きに分解。例: (i) … / (ii) …}
素材:
- {…}
接続: {なぜこの順序か（前セクションからの繋がり）}

### 展開2: {見出し案}
...

### 結び: {見出し案}
展開する思考:
- {どう着地するか}
残す問い:
- {未解決のまま読者に委ねること}

## 参考資料との接続
| 参考資料 | 記事での活用方法 |
|---|---|
| {資料名} | {どのセクションで、どう言及するか} |
```

outline.md は最新が正。構成を見直すたびに上書きする（変遷は git 履歴で追える）。

構成設計で新たに出てきた参考情報があれば `$OUTPUT_DIR/references.md` に追記する。

## 3. 確定後

1. 地図を更新する（SKILL.md「地図の更新」）
2. 隔離レビューの `drift outline` を提案する（著者が頷いたら実行する）
3. 著者に返すのは、outline.md のパス・章の並び（見出しだけ）・地図の URL とその変更点1〜2行

## やらないこと

- outline.md に本文の文章を書く
- thinking.md に無い主張を構成の都合で足す（必要なら掘る工程へ戻す）
- 想定反論への先回りを章として立てる（駐車場へ送る）
