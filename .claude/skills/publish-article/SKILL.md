# 記事成果物の公開

`output/{yyyymmdd}_$ARGUMENTS/`（非公開の作業層）から、公開してよい成果物だけを `published/{yyyymmdd}_$ARGUMENTS/`（公開層）へ選別コピーし、公開適性を点検して、著者の承認後にコミットする。

このリポは Public であり、published/ に commit したものは誰でも読める。このスキルは「思考の過程ごと共有する」というブログの方針と、「推敲前の生素材・実生活に波及する記述は出さない」という線引きを両立させる公開ゲートである。何を出すかの最終判断は著者が握る（勝手にコミットしない）。

**フォルダ命名規則**: 対象は `output/{yyyymmdd}_$ARGUMENTS/`。`$ARGUMENTS` に日付プレフィックス付きのフォルダ名が直接渡された場合はそのまま使う。以降 `$OUTPUT_DIR` は作業層側、`$PUB_DIR` は `published/` 側の同名ディレクトリを指す。

## 手順

### 1. 対象と選別リストの確認

- `$OUTPUT_DIR` が存在しなければ、その旨を伝えて終了する。
- 既定のホワイトリスト（存在するものだけコピー対象にする）:
  - `core.md` / `references.md` / `thinking.md` / `outline.md` / `draft.md` / `draft_user.md`
  - `draft_user_*.md`（言語版など、著者が公開した最終版の派生）
  - `brief.md` は旧記事にだけ存在する（新記事では作らない）。あれば既定の対象に含める
- opt-in（著者がこの実行で明示的に指定した時のみ対象に加える）:
  - `review/`（lens 別ファイル: `critique_NN.md` / `drift_NN.md` / `readers_NN.md` / `author_NN.md`）/ `comparison/`
  - 旧記事に残る `critique/` / `drift/` / `readers/` / `brief_deepen.md` も同じ扱い
  - 工程の実演として過程ごと見せたい記事だけ、著者の指定で公開する。
- 常に除外（指定されても公開層に入れない）:
  - `references/`（第三者の raw 素材。gitignore でも二重に防いでいる）
  - `map.html`（計画の見取り図。正本は Markdown 側にあり、gitignore の `*.html` とも整合させる）
  - `*.mhtml` / 画像 / `pre-discussion/` などの未整理メモ / `draft_pre-tighten.md` / `draft_v2.md` 等の途中版
- コピー予定の一覧を著者に提示してから次へ進む。`$PUB_DIR` に既存ファイルがある場合は上書きになることを明示する。

### 2. コピー

ホワイトリストのファイルを `$PUB_DIR` へコピーする（ディレクトリが無ければ作成）。

### 3. 公開適性の点検

コピー後の `$PUB_DIR` 側ファイルを、以下のレンズで通読して点検する。該当箇所は `ファイル名:行番号` で指摘し、**本文を勝手に書き換えない**。

1. **職場・人間関係・進退**: 離職・転職の意向、同僚・上司・特定個人への評価など、実生活の関係に波及する記述。
2. **本人以外の実名**: 記事本文で公開済みの一次体験の言及（登壇者名等）は可。非公開文脈での人物評・私的なやりとりは不可。
3. **第三者素材の転記**: X ポスト・記事本文・PDF の長文写しが .md 内に残っていないか（要旨化・短い引用＋出典は可）。
4. **公開版で落とした生素材**: 公開記事（draft_user.md）と照らし、著者が記事に載せないと判断した内心・感情の一次素材が brief / thinking に残っていないか。残っていれば「これも公開してよいか」を個別に確認する。
5. **認証情報・識別子**: トークン・メールアドレス・アカウント ID・個人マシンの絶対パス。

補助として、職場・進退系の語彙（例: 離職, 退職, 転職, 同僚, 上司, チームメンバー）を Grep で機械的に走査してよい。機械走査は見落とし防止の補助であり、通読の代替にしない。

### 4. 著者の承認

- 点検結果（指摘ゼロならその旨）とコピーしたファイル一覧を提示し、著者の判断を待つ。
- 指摘への対処（該当箇所の削除・言い換え・そのまま公開）は著者が決める。対処の実施は published/ 側のファイルにのみ行い、output/ 側の原本は変更しない。

### 5. コミット

著者の承認後に `$PUB_DIR` を git add し、`published: {テーマ} の記事成果物を公開` の形でコミットする。承認前にコミットしない。push は著者の指示があった時のみ行う。
