# 記事計画の見取り図

`output/{yyyymmdd}_$ARGUMENTS/` の計画を1枚の HTML にレンダリングし、`$OUTPUT_DIR/map.html` に出力する。

**フォルダ命名規則**: 出力先は `output/{yyyymmdd}_$ARGUMENTS/` とする。既存フォルダがあればそれを使う。`$ARGUMENTS` に日付プレフィックス付きのフォルダ名が直接渡された場合はそのまま使う。以降のパス記述で `$OUTPUT_DIR` はこのディレクトリを指す。

## このスキルの役割

著者が「この設計で書き始めてよいか」を一度に見て判断するための材料を作る専任。brief.md も outline.md も読み下す形式であり、章と章の関係・軸の射程・落とした論点が同時に視界に入らない。その1点だけを解く。

**このスキルは判定しない。** 出力は計画のレンダリングであって、指摘・評価・優先度付きの findings ではない。良し悪しの判断は著者が下す。

工程内での役割分担を守る（重複させない）:

- **critique**: thinking.md の主張そのものの是非を叩く。本スキルは是非を問わない
- **check-drift**: 前段と後段の provenance（何を落とし何を足したか）を点検する。答えは2文書の差分に閉じており、AI が判定できる。本スキルが扱うのは「この計画で書きたいか」で、答えは著者の中にしかない
- **outline**: 構成そのものを著者と対話して設計する。本スキルは設計しない。既にある計画を写すだけ

`/check-drift` と同じタイミングで走らせる場合は、**check-drift が先、本スキルが後**。drift の修正は計画を書き換えるため、先に地図を描くと二度描くことになる。

## 守る規範

1. **レンダリングに徹する**。分析・評価・改善提案を HTML に書かない。書けるのは、入力ファイルに既にある内容の写像だけ
2. **正本を二重化しない**。正本は Markdown（brief.md / thinking.md / outline.md）。HTML は一方向の写像であり、著者が HTML を手で直すと乖離する。変更は Markdown 側に入れて再生成する。この旨をフッタに明記する
3. **推測で埋めない**。入力に無い箇所は `未定` として表示する。確信で埋めた偽の計画は空欄より悪い（CLAUDE.md「真正性 > 網羅」）。**埋まっていない箇所が見えること自体が、この地図の価値の半分**
4. **デザインを発明しない**。`${CLAUDE_SKILL_DIR}/templates/map-template.html` の構造とトークンをそのまま使う。記事間で見た目を揃え、浮いた時間は中身の写し取りに使う
5. **出力は output/ に置く**。`published/` へは持ち出さない（CLAUDE.md「公開境界」）
6. **上書きする**。`map.html` は最新が正。世代を `map_NN.html` として溜めない。計画の推移は本スキルの担当外

## 手順

- [ ] 1. 入力を読み込む
- [ ] 2. 6つの要素を抽出する
- [ ] 3. テンプレートから map.html を生成する
- [ ] 4. 検算する
- [ ] 5. 承認を求めるサマリを返す

### 1. 入力の読み込み

`$OUTPUT_DIR` から読む。すべて「あれば読む」であり、揃っていなくても中断しない。

| ファイル | 地図のどこに写るか |
|---|---|
| `brief.md` | コアメッセージ、読者、扱わない領域 |
| `thinking.md` | 各章の主張、貫く軸 |
| `outline.md` | 章の順序、見出し、分量配分、素材の接続 |
| `references.md` | 各章の素材の出典表示 |

`brief.md` と `thinking.md` の両方が無い場合のみ、地図を作らずに「先に `/brainstorm` または `/deepen` を回してください」とサマリで返して終了する。片方でもあれば、埋まらない箇所を `未定` にして描く。

`outline.md` が無い場合、章の行は thinking.md の主張の並びで代替し、順序が未確定である旨をヘッダの meta に明示する。

### 2. 抽出

入力から次の6つを取り出す。**それぞれ、どの入力ファイルの記述に対応するかを言えること**を条件にする。言えないものは書かない。

1. **主題（thesis）**: この記事の一番伝えたい一文。brief.md / outline.md のコアメッセージから採る
2. **章**: 順序・見出し・想定分量。分量はゲージの相対値になるので、最大の章を 100% として比率を出す
3. **章ごとの3層**: 主張（その章で立てる一文）／論点（扱う論点のラベルと、扱い方の注意）／素材（使う具体・エピソード・資料と、その出典ファイル名）
4. **貫く軸**: 複数の章をまたいで走るもの（通奏する問い、用語の定義、判定軸、一次素材）。開始章と終了章を持つ
5. **記事が答える問い**: 読者が持ち込む問いと、記事が返す答え、返す章
6. **扱わないこと**: 意図的に外した領域と、その行き先（別記事・既刊・短く済ませる・書かない）

重心（最も重い章）が特定できるなら1つだけ `hot` として強調する。複数を強調しない。重心が読み取れないなら強調しない。

### 3. 生成

`${CLAUDE_SKILL_DIR}/templates/map-template.html` をコピーし、プレースホルダを置換して `$OUTPUT_DIR/map.html` に書き出す。CSS は変更しない。

構造は次の通り。テンプレートのコメントに対応が書いてある。

- **ヘッダ**: eyebrow（日付）／タイトル／リード文／thesis／meta（分量・章数・主張数・軸数）
- **Map**: 6列前後のグリッド。行は上から `章` `主張` `論点` `素材`、その下に `貫く軸` の帯を `grid-column` で渡す
- **Questions**: 記事が答える問いのカード
- **Boundaries**: 扱わない領域と行き先の2列
- **フッタ**: 正本がどのファイルかの明示と、HTML を手で直さない旨

章の数がテンプレート（6列）と違う場合は `grid-template-columns` の `repeat()` の数だけ合わせる。他は触らない。

### 4. 検算

書き出した後に確認する。1つでも満たさなければ直してから次へ進む。

- 地図上のすべての記述が、入力ファイルのどこかに対応しているか。対応を言えない記述が1つでもあれば削る（規範3）
- 評価・提案・指摘の語（「〜すべき」「〜が弱い」「改善」）が本文に混ざっていないか（規範1）
- 埋まらなかった箇所が `未定` として可視化されているか。黙って省略していないか
- ブラウザで開いた時に横スクロール以外で崩れないか。`.mapwrap` の外に溢れていないか

### 5. サマリ

メイン会話には**実行サマリのみ**を返す。地図の内容を戻り値に詰めない。含めるのは次の4点。

1. 出力パス（`$OUTPUT_DIR/map.html`）
2. 描いた規模（章 N 本、主張 N 本、貫く軸 N 本、扱わない領域 N 件）
3. `未定` として残した箇所の一覧
4. 著者に返す3つの問い: **この重心でよいか／外した領域はこれでよいか／未定の箇所は書き始める前に埋める必要があるか**

判断は著者が下す。承認・却下・修正指示を待つ。AI が地図を作って AI が承認する形にしない。
