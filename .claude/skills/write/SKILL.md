# 記事執筆・推敲

brief.md（必須）と outline.md・thinking.md（あれば）をもとに記事本文を執筆し、`output/{yyyymmdd}_$ARGUMENTS/draft.md` に出力する。執筆後、圧縮パス → 機械 lint → 自己レビュー → 読者シミュレーション → 著者との磨きこみ、の順で推敲する。

**フォルダ命名規則**: 出力先は `output/{yyyymmdd}_$ARGUMENTS/`。既存フォルダがあればそれを使う。`$ARGUMENTS` に日付プレフィックス付きのフォルダ名が直接渡された場合はそのまま使う。以降 `$OUTPUT_DIR` はこのディレクトリを指す。

## 前提

- Node.js と `npm install` 済みであること（機械 lint が textlint を使う）。未導入なら lint は「textlint が未導入です」と返すので、数値仕様の判定だけで進めてよい
- `${CLAUDE_SKILL_DIR}/references/voice-style.md` が文体の正。**0. 数値仕様と 1. 実例を先に読む**。ルールは実例で伝わらない判断を補うもの

## 手順

### 1. 準備

以下を読み込む:
- `$OUTPUT_DIR/brief.md`（必須。なければ「先に `/brainstorm $ARGUMENTS` を実行してください」と案内して終了）
- `$OUTPUT_DIR/outline.md`（あれば。見出し構成・展開順序・資料接続の設計図）
- `$OUTPUT_DIR/thinking.md`（あれば。各セクションで展開する主張・素材）
- `$OUTPUT_DIR/references.md`（あれば。参考リンクを本文中に配置するため）
- `${CLAUDE_SKILL_DIR}/references/voice-style.md`（必須）

### 2. 執筆

voice-style.md に従い、Markdown で記事本文を書く。

- outline.md があればその見出し構成・展開順序に沿い、各セクションを thinking.md の主張・素材で肉付けする。無ければ thinking.md → brief.md のストーリーラインの順で頼る
- **冒頭は宣言スタートが既定**（voice-style ルール19）。「この記事では〜について書きます」＋スコープ 1〜3 文＋執筆動機 1〜2 文。参加記だけ体験スタート。参考資料ブロック・固定ヘッダ・著者プロフィールは書かない
- 段落は 1〜2 文。事実・年表・並列は箇条書き、思考は散文（ルール11）
- 参考リンクは本文中の該当箇所に短い導入＋タイトルの箇条書きで分散させる
- 画像の挿入位置は `<!-- 画像: {説明} -->` で示す
- **✍️ 可視マーカーは AI が一次情報を持たない箇所だけ**。特定の瞬間の一次感情・私的体験など brief.md / thinking.md から確認できない素材を、引用ブロック `> ✍️ ここに〇〇を一次感情で（仮置きは過去記事ベース、著者が上書き）` として残す。導入の執筆動機は ✍️ にせず AI が書く
- **ℹ️ 引き継ぎメモ**をドラフト冒頭に引用ブロックで置く。本文に入れなかった反論への返し・出典の性質・削った保険文を「コメント欄で突かれたら返す用」として列挙する。本文には出さない

**出力**: `$OUTPUT_DIR/draft.md`

### 3. 圧縮パス

`/tighten-draft $ARGUMENTS` を実行する（fork。書いた当人から切り離して削る）。保険文・章間の道案内・多段論証・結びの定型・「」の減量・3 文以上の段落の分割を、数値仕様（voice-style「0.」）に収まるまで行い、draft.md を上書きする。削った保険文は ℹ️ メモへ移す。

戻ってきたサマリ（前後の指標・削った件数）を確認する。背骨（thinking/outline の主張）が落ちていたら、圧縮を巻き戻すのではなく該当主張を短く書き戻す。

### 4. 機械 lint

```
node scripts/lint-draft.mjs $OUTPUT_DIR/draft.md
```

- NG がゼロになるまで直して再実行する（最大 3 周）。数値仕様・禁止句・冒頭／結びの型・textlint の error を対象にする
- 直さない判断をした項目は、理由を ℹ️ メモに 1 行で残す（例: 「英文引用 4 文: dbt 原文が主題のため維持」）
- PostToolUse hook が設定されていれば、以降の Edit/Write のたびに同じレポートが自動で返る。手動実行と読み方は同じ

### 5. 自己レビュー

lint では見えないものだけを読み返す（voice-style「生成後の点検」の 2）:

- 実例 2〜4 の手触りに近いか（体温の出し方、反論を認めたまま次へ進んでいるか、引用素材を 1 段で渡しているか）
- 論理の飛躍: 読者が「なぜ急にこの話に？」と感じる箇所
- コアメッセージ: brief.md のコアメッセージから逸れていないか
- 見出しが節のオチを言い切っていないか、批判の向きが我々ユーザー側か、固有名詞が抽象化されていないか
- **導入の事後確認**: 本文を確定させた後に導入を読み直す。(a) 予告した論点が本文で回収されているか、(b) 執筆動機が本文の主張・結論と整合しているか、(c) 導入で挙げた具体例が本文で展開されているか。ズレていれば導入を直す

### 6. 読者シミュレーション

`/simulate-readers $ARGUMENTS` を実行する（fork）。初見の読者視点（brief.md の読者像＋懐疑側・前向き側）での離脱点・反応・行動変化・炎上経路の予測を得る。

**指摘反映の採否基準（主題か、鎧か）**: 自己レビュー・simulate-readers・check-drift の指摘を反映する時は、修正ごとに「この修正は記事の主題を深めるか、想定反論への鎧を増やすだけか」を問う。

- 主題を深める修正（例: 自己矛盾を隠さず明示することが、誠実さを主題とする記事ではそのまま主題の実演になる）→ 本文に反映する
- 鎧を増やすだけの修正（想定反論の先回り潰し・括弧書きの防御ヘッジ・補足条件の列挙）→ 本文に入れず ℹ️ メモに残す。大域のヘッジ（「保証できない」の一文）に論理的に包含される個別の先回りは足さない

反映後に手順 4 の lint を再実行する。

### 7. 著者への提示と磨きこみ

- 全文を一度に出さず、「全体の流れ」「lint の残件と直さなかった理由」「特にフィードバックがほしい箇所」を添える
- 構成上の判断（なぜこの順序にしたか）があれば簡潔に説明する
- フィードバックの反映 → lint → 再提示、を著者が満足するまで繰り返す。反映で本文が膨らんだら手順 3 の圧縮パスをもう一度回す
- 承認ゲートとして `/check-drift $ARGUMENTS draft` を回し、前段からの背骨落ち・無根拠 add が無いことを確認してから完了へ進む

### 8. 完了

- 「`$OUTPUT_DIR/draft.md` に最終版を保存しました」
- 「Wix への書き起こし時に、画像プレースホルダー（`<!-- 画像: ... -->`）を実際の画像に差し替えてください」

空の `$OUTPUT_DIR/draft_user.md` を生成する（既に存在する場合はスキップ）:
- 「ユーザー推敲版用に `draft_user.md` を空白で作成しました。AI 版を参考にしながら、ご自身の言葉で書き直したり、独自の構成で書いたりしてください」
- 「公開後、`/compare-drafts $ARGUMENTS [公開URL]` で AI 版と公開記事を比較すると、次回以降の生成を著者に近づける改善案が得られます」
