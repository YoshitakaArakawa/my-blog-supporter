# 核と掘る（ブログと登壇に共通の上流）

著者と対話しながら、1本の記事または登壇の中身を **核 → 掘る** の順で固める。組む・書く工程へは、core.md の `形式:` に応じて渡す。原則と不変条件は CLAUDE.md が正で、ここでは工程として適用する。

引数: `$ARGUMENTS`（1つ目がテーマ、2つ目が工程 `core` / `deepen` / `map`。どちらも任意）

成果物は `output/{yyyymmdd}_{テーマ}/`（`$OUTPUT_DIR`）に置く。既存フォルダがあれば新規に作らずそこへ書く（テーマに日付プレフィックスが付いていればそのまま使う）。テーマが渡されていない時は `output/` の既存ディレクトリと著者の発言から決め、新規なら実行日を `{yyyymmdd}` に使う。

## 起動と現在地

起動したら、まず `$OUTPUT_DIR/core.md`・`$OUTPUT_DIR/thinking.md` の「スコープ」節と「未決」節・`$OUTPUT_DIR/map.html` の有無を読む（無ければ「無い」と分かればよい）。そのうえで **現在地を3行で報告し、必要な問いを返す（無ければ返さない）**。

- 核: core.md の問いと形式
- 進捗: 掘った論点数と、組む・書く工程の状態。ブログなら構成・ドラフトの有無と公開状態（Wix は `published.md`、リポの公開層は `published/{記事}/` の有無）、登壇なら storyline.md・deck.md・Google スライドの有無
- 未決: thinking.md の未決から1件

引き継ぎ文書（handoff.md 等）は作らない。状態はファイルが持つ。長い要約を返さない。

工程は2つ目の引数があればそれにする。無ければ次で決める。

- core.md が無ければ **核**。あって thinking.md が無い、または著者が掘りたいと言えば **掘る**
- 2つ目の引数が `map` なら地図の再生成だけを行う
- 著者が構成・本文・スライドに進みたいと言えば、「組む・書く工程へ渡す」に従う

## 工程1: 核

対話で5行と形式を起草し、著者の承認を得て `$OUTPUT_DIR/core.md` に書く。**AI が起草してよいが、文言を承認するのは著者**。承認が取れるまで次の工程に進まない。

- 5行・各1文・各行 120 字以内。骨格は [templates/core-template.md](templates/core-template.md) を読む
- `形式:` の行で媒体を決める（`ブログ` か `登壇 {持ち時間}（{場}）`）。登壇なら「読者」は聴衆、「読後」は聞き終えた後のこと
- 記事から登壇を起こす時（逆も）は、元の core.md・thinking.md を素材として読み、核は新しく承認する。媒体が変われば受け手と読後が変わるため
- 参考 URL が対話で出たら references.md に1行（タイトル・URL・一行要旨）で控える。本文の取得は掘る工程で必要になった時に行う（不変条件4）

## 工程2: 掘る

発散（横に広げる）と深掘り（縦に厚くする）を1つの対話で行い、`$OUTPUT_DIR/thinking.md` を作る・更新する。**掘ることに専念し、記事の見出し構成やスライドの構成は設計しない**。詳細な手順・問いの例・thinking.md のテンプレートは [references/phase-deepen.md](references/phase-deepen.md) を読む。

- critique は提案に留める（「主張を叩いておきますか」の一言）。著者が「叩いて」「反論ある？」「穴を見て」と言ったら、`Skill` ツールで `review` を引数 `"{テーマ} critique"` で起動する（不変条件7）。`{テーマ}` には `$OUTPUT_DIR` の決定に使ったテーマを渡す
- 戻ってきた指摘は3件まで、各指摘に効く core 行が付いている。採否には「本質的」4条件（phase-deepen.md）を当てる。反映する時は修正ごとに「この修正は主題を深めるか、鎧を増やすだけか」を問い、後者は駐車場へ送る（不変条件5）

## 組む・書く工程へ渡す

thinking.md のスコープが固まり、著者が構成・本文・スライドに進みたいと言ったら、core.md の `形式:` で渡す先を決め、`Skill` ツールで起動する。`形式:` の行が無い core.md（形式の行を足す前に作った記事）はブログとして扱う。

| 形式 | 渡す先 |
|---|---|
| ブログ | `blog-write`（組む・書く） |
| 登壇 | `presentation-write`（場・組む・書く） |

渡す前に、会話でだけ決まったことが core.md（改訂行）と thinking.md に書かれているかを確かめる。書かれていないことは次の工程にもセッションにも渡らない。

## 地図の更新

`$OUTPUT_DIR/map.html` は計画の見取り図であり、**「この設計で書き始めてよいか」を著者が一目で判断するための合意ゲート**。抽出結果を `$OUTPUT_DIR/map.json` に書き、`node ${CLAUDE_SKILL_DIR}/scripts/render-map.mjs $OUTPUT_DIR/map.json` で map.html を生成する（詳細は [references/map-spec.md](references/map-spec.md)）。生成は隔離せず、この対話の中で行う。登壇の構成の俯瞰は、presentation-write のストーリーボードが担う。

| きっかけ | 扱い |
|---|---|
| core.md の承認直後 | 自動で生成する |
| thinking.md のスコープ確定後 | 自動で更新する |
| outline.md の確定後（blog-write から `map` の引数で呼ばれる） | 自動で更新する |
| 著者が方針転換を口にした後 | 「地図を更新しますか」と提案する |
| 著者が「地図」「全体像」「俯瞰したい」と言った時 | 更新して返す |

**著者に返すのは「地図: {URL またはパス}」と変更点1〜2行だけ**。地図の内容を会話に貼らない。
