# lens: readers（初見読者として通読）

## 目次

- 入力
- 画面の撮り方と読み方
- 観点（ペルソナの設計／シミュレーション／画面で読む／編集者視点）
- ペルソナの置き換えと並列
- 出力テンプレート
- やらないこと

AI が生成した記事ドラフトを **初見の読者として通読** し、読中体験・読後の反応・行動変化・炎上経路を予測する。ドリフト点検や文体チェックでは出ない種類の問題——どこで読者が離脱するか、どの一文が刺さるか、どの段落が切り取られて燃えるか、読後に行動が変わるか——を公開前に捕まえる。

執筆時の意図や経緯を知らない読者の体験を近似するのが目的。「公開された記事」としてだけ読む。読者は Markdown ではなく画面で記事を読むので、本文に加えてプレビューを**スマホ幅とデスクトップ幅の画面**として読み、図の位置・効き方・スマホでの読みやすさも見る。

## 入力

- **対象ドラフト**（必須）: 対象欄（`$2`）が `.md` で終わるならそのファイル名、それ以外・空なら既定の `draft.md`。`$OUTPUT_DIR/{対象ファイル名}` を読む。無い・空の場合は「対象が見つからないので点検していない。先に `/blog-write` で書く工程を回してください」という旨をサマリで返して終了する。対象欄にペルソナの形式（`ラベル: 説明`）が入っていたら、対象の省略とみなして `draft.md` を読み、その値をペルソナとして扱う
- **画面**（既定で撮る）: 対象ドラフトのプレビューを、スマホ幅とデスクトップ幅の連番の画面に撮ったもの。撮り方と読み方は次節
- `core.md` の「読者」行と「読後」行**だけ**をペルソナ設計に使う。「動機」「現在地」行は優先順位の判定に使うだけで、ペルソナには持ち込まない——初見読者は著者の意図を知らないため
- `thinking.md` / `outline.md` / `references.md` は**読まない**。初見読者はこれらを知らない

**読者には見えない要素を除外する**: ドラフト冒頭の作業メモ（ℹ️ 引用ブロック）、✍️ 可視マーカー、HTML コメントは著者向けであり、読者体験の評価対象から外す。✍️ 部分は「ここに著者の一次体験が入る前提」で読む。未作図の図（`<!-- 画像: … -->`）は、画面では点線の枠として出る。「説明どおりの図がここに入る前提」で読み、図の位置の点検には含めるが、見た目は評価しない。

## 画面の撮り方と読み方

1. **今回のファイル名を先に決める**。SKILL.md 手順5の連番で決める（ペルソナ指定時は「ペルソナの置き換えと並列」のラベル付きの名前）。画面のフォルダ名に使うため、読み始める前に決める
2. **リポジトリのルートで撮る**:

   ```
   node scripts/shoot-preview.mjs $OUTPUT_DIR/{対象ファイル名} --out-dir $OUTPUT_DIR/review/screens/{今回のファイル名から .md を除いた名前}
   ```

   スマホ幅（390×844）の画面が `mobile_NN.png`、デスクトップ幅（1280×1000）の画面が `desktop_NN.png` に、上から1画面ずつ連番で出る。見出しと図がどの画面にあるか、スマホ幅での図の縮尺、図の無い区間の長さは `screens.json` に出て、その要約が標準出力に出る
3. **通読はスマホの画面で行う**。`mobile_01.png` から順にすべて読み、どの画面で引き込まれ、どの画面で離脱しそうかを画面番号つきで記録する
4. **引用と箇所の特定は Markdown で行う**。文字の正は Markdown であり、画面の文字を写し取らない
5. **デスクトップの画面は、図を含む画面だけ読む**（`screens.json` の `blocks` の `screen`）。スマホとの見え方の差を見るために使う
6. **図の原寸を読む**（`screens.json` の `src`。対象ファイルからの相対パス）。図中の文字の大きさと要素の並びを確かめる

規律:

- 1枚の縦長の全体像（`--full-page`）に撮り直さない。縦長の画像は読む側で縮小され、本文の文字が読めなくなる
- 撮影に失敗した時（playwright-cli が無い等）は、本文だけで点検を続ける。`## 画面で読んだ所見` とサマリに、画面を読めていないことと理由を書く。画面の観点を推測で埋めない

## 観点

### ペルソナの設計

3つのペルソナを立てる:

1. **主読者**: core.md の「読者」行をそのまま使う
2. **懐疑側の読者**: 記事の主張に乗らない合理的な読者。記事が想定する反論を実際に抱えている人
3. **前向き側の読者**: すでに主張に共感している読者。シェア・引用するかどうかの目線

記事のテーマに応じて 2・3 は具体化してよい（例: 特定コミュニティの中堅ユーザー、同業の実務者）。誰を立てたかは出力に明記する。

ペルソナ欄（SKILL.md 手順1）に値があれば、この3者の代わりにその1人で読む（「ペルソナの置き換えと並列」）。

### シミュレーション

各ペルソナで通読し、次を記録する:

- **読中体験**: どこで引き込まれ、どこで離脱しそうになり、どこで反発・疑問を感じたか（該当箇所の引用と、スマホの画面番号つき）
- **読後の一言**: その読者が SNS に書きそうなポスト文面を1つ想像する
- **行動変化の予測**: core.md の「読後」行が起こるか。変わらないなら何が障壁か
- **コメント欄の予測**: 書かれそうな指摘・質問・反論

### 画面で読む

画面を読めた時は、ペルソナを離れて次の4点を見る。拾った問題は編集者視点の弱点と同じ列に並べ、共通骨格の指摘（最大3件）か駐車場へ送る。

- **文章の続きすぎ**: `screens.json` の `gaps`（図の無い区間を画面の高さで測ったもの）で、スマホで図の無い区間が何画面続くかを見る。目安は3画面を超える区間。その区間の画面を見て読者がどこで離脱しそうかを判断し、図・一覧・節の切り方のどれで区切ると効くかを方向性として書く
- **図の位置と本文との重複**: 図が説明する本文の近くにあるか（何画面離れているか）。図と本文が同じことを二度言っていないか（図を見れば分かることを本文が逐一なぞる、本文で言い切ったことを図が繰り返すだけ）。図が無いと伝わらない関係を図が担っているか
- **スマホ幅での図中の文字**: 原寸の図で最小の文字の高さ（px）を見積もり、スマホ幅の `scale`（表示幅 ÷ 原寸の幅）を掛ける。目安は 11px で、下回れば読めない候補としてスマホの画面で実際に読めるかを確かめる。縦長の画像（スマホの画面写真など）はプレビューで本文幅の半分に出るので、スマホでは縮尺がさらに小さい
- **図と直後の一覧の並び順**: 図の要素の並び（左から右・上から下・番号）と、直後の箇条書きや本文の言及の順が一致しているか。原寸の図と Markdown を突き合わせる

### 編集者視点

ペルソナを離れて次をまとめる:

- **最大の強み1つ**: 推敲で削られないよう明示する
- **直すと効果が大きい弱点**: 該当箇所の引用＋直し方の方向性つき。共通骨格の指摘（最大3件）に載せ、それ以下は駐車場へ
- **炎上・誤読リスク**: 切り取り引用されたとき別の意味になる段落、立場の違う読者に攻撃と映る表現

## ペルソナの置き換えと並列

ペルソナ欄に値があれば、既定の3者の代わりに、その1人の読者として読む。依頼側が複数の読者に互いに独立して読ませたい時は、ペルソナごとに別の起動にして並列で回す。

- **形式**: `{ラベル}: {説明}`。ラベルは英小文字・数字・ハイフンで書き、ファイル名に使う。ラベルが無い・形式に合わない時は点検せず、形式を示してサマリで返す
- **core.md の「読者」行**: ペルソナには使わず、指摘の優先順位の判定にだけ使う。ペルソナが「読者」行から外れていれば、`## 対象` にその旨を書く
- **並列の例**（ダミー）: 2つの起動を同時に出す

  ```
  /review 20261201_example readers draft.md "expert: 業務で BI ツールを5年以上使い、ダッシュボードを日常的に作る人"
  /review 20261201_example readers draft.md "novice: BI ツールを触り始めて1か月の人"
  ```

ファイル名と連番:

- ペルソナ指定時のファイル名は `review/readers_{NN}_{ラベル}.md`、画面のフォルダは `review/screens/readers_{NN}_{ラベル}/`
- NN は、ラベル付きも含む `review/readers_*.md` の最大番号 + 1。ペルソナを指定しない時も同じ数え方をする
- ラベルが違えば、並列の起動が同じ NN を選んでもファイルは衝突しない
- 書く直前に同じ名前のファイルがあれば、NN を1つ上げる。上書きしない
- `## 前回からの変化` は、同じラベルの前回のファイルと比べる。無ければ直近の `readers_*.md` と比べる

## 出力テンプレート

見出しは `読者シミュレーション`。`## 対象` 節には「{対象ファイル名}（ペルソナ: {一覧}／画面: スマホ {n} 画面・デスクトップ {m} 画面。読めなかった時は「画面: 読めていない」）」を書く。

lens 固有の追加節として、`## 指摘` の**前**に次を置く:

```markdown
## ペルソナ別の読書体験

### 1. {主読者の名前}
- 引き込まれた箇所: {引用＋理由（スマホ {NN} 画面目）}
- 離脱・反発した箇所: {引用＋理由（スマホ {NN} 画面目）}
- 読後の一言（SNS想定）: {ポスト文面}
- 行動変化: {予測と根拠}
- コメント欄の予測: {箇条書き}

### 2. {懐疑側} / ### 3. {前向き側}
{同構成。ペルソナ指定時は1人だけ}

## 画面で読んだ所見
- 画面: review/screens/{今回のファイル名}/（スマホ {n} 画面・デスクトップ {m} 画面）。撮れなかった時はその理由
- 図の無い最長の区間: スマホ {x} 画面（{どこから} → {どこまで}、{NN}〜{NN} 画面目）
- 図ごと:
  - {図のファイル名}（スマホ {NN} 画面目・縮尺 {scale}）: {位置／本文との重複／スマホでの文字／並び順のうち、引っかかった点。無ければ「問題なし」}

## 最大の強み（削らないこと）
{1つ、引用つき}
```

`## 指摘` の**後ろ**に次を置く:

```markdown
## 炎上・誤読リスク
{切り取り・誤読の経路と緩和の方向性。無ければ「なし」}
```

各指摘の項目:

```markdown
### 1. {弱点の見出し}
- 効く core 行: {問い / 読者 / 読後 / 動機 / 現在地 のどれに、どう効くか}
- ペルソナ: {どの読者がどう躓くか}
- 箇所: {該当箇所の引用。画面に関わる時はスマホの画面番号も}
- 問題: {読者体験として何がどう損なわれるか}
- 直し方の方向性: {どう直すか（書き換え案は書かない）}
```

サマリには、`駐車場` の行の前に `画面: スマホ {n} 画面を読んだ`（読めなかった時は `画面: 読めていない（{理由}）`）を1行足す。

## やらないこと

- 前段ファイルとの照合（lens=drift の領分）
- 主張そのものの是非の議論（lens=critique の領分）。この lens は**読者にどう受け取られるか**だけを見る
- 著者が書いた原稿（`draft_user.md`）の対象化（lens=author の領分）
- ドラフトの書き換え。指摘の採否は `/blog-write` の書く工程で著者が判断する
- 図の描き直し（`/illustrate` の領分）。図の問題は直し方の方向性だけ書く
- プレビューと Wix の表示の差の指摘。プレビュー（`scripts/render-preview.mjs`）は公開時の見た目の近似である
- 配色・書体・余白の好みの議論。読みやすさに効く時だけ扱う
